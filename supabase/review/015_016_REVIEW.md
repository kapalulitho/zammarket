They depend on existing verified/completed-profile helpers (009/010 baseline); neither depends on held 013_v2/014_v2 or changes migration 012. ## 015 Property Marketplace

Tables and columns:

- property_listings: id, owner_id, title, property_type, purpose, location, description, price, price_basis, bedrooms, bathrooms, area_sqm, agent_type, agent_name, media_paths, status, created_at, updated_at.
- property_saved: user_id, property_id, created_at; composite primary key prevents duplicate saves.
- property_enquiries: id, property_id, sender_id, recipient_id, body, reply, created_at, updated_at.

Functions: property_listing_guard (verified completed owner, immutable identity, server-derived agent_name, existing own-folder image validation), property_enquiry_guard (publisher recipient, immutable thread, five sends/minute, recipient-only reply), property_image_visible (boolean published-reference check), property_capabilities (frontend schema readiness). Guard functions are trigger-only, revoked from clients; the image visibility helper and capability RPC are executable by API audiences with an empty search_path. No private data is returned by capability RPCs.

Two triggers; RLS on all three tables. Fifteen new policies: published-or-owner read and owner insert/update (3); private saved read/insert/remove (3); participant enquiry read, verified sender insert, recipient reply (3); private Storage read/read guard, own-folder upload/upload guard, no overwrite and no delete (6). Column grants prevent client identity/reply injection. Seven indexes including three primary keys; discovery and owner indexes plus sender/recipient enquiry indexes.

New PRIVATE property-media bucket, JPG/PNG/WebP only, 5 MB/image, eight paths/property. Image signing allows owner or any published reference; restrictive policies defend against other permissive Storage policies. Closure blocks new public signing, not already issued 60-second links or copies. Fields in a published property row (including publisher UUID, self-declared agent type and display name) are public by design. No exact-address, private contact, identity-document or financial fields are added. Seller profile contact visibility remains enforced by existing profile infrastructure.

Client property deletion is not granted; closure/editing retains records/photos. Removing a saved-property association is allowed only to its owner and does not delete the property. FK deletion defaults block hard deletion of referenced users/properties rather than cascading. No listing/photo cleanup, bookings, deposits, commissions or payments.

## 016 Delivery planning foundations

Tables and columns:

- delivery_drafts: id, customer_id, pickup, destination, description, parcel_size, weight_kg, notes, state, created_at, updated_at. Only state is planning.
- courier_profile_drafts: owner_id, display_name, vehicle, service_area, about, state, updated_at. Only state is draft; no verified/active courier claims.

Functions: delivery_plan_guard, courier_profile_draft_guard, delivery_capabilities. Two owner/membership/identity triggers; six RLS policies (read/insert/update per table). Trigger functions run as invoker with empty search_path and no direct execution grants; existing membership helper performs its established verification checks. Column grants exclude state and ownership updates. Customer/time index and owner primary key support private dashboards.

No public data projection, driver assignment, exact recipient contacts, payment/quote fields, tracking, service-provider integrations or delivery-state transitions. Ordinary users cannot read another customer's plan or courier draft. No client delete privileges. Frontend courier profile remains design-only; saving that draft is not connected yet. Customer private-plan saving/history is prepared behind the capability gate.

## Safety and limits

Only new objects are created. Existing accounts, product listings, likes, messages, profile definitions and photos are not rewritten. 015 adds policies to storage.objects but does not replace existing policies or bucket settings; 016 adds none. Review all existing permissive/restrictive policies in real staging before approving effective Storage access.

Transactions use 5s lock/60s statement timeouts. Statement failure before commit permits full transaction rollback. After commit and new records, preserve data and prefer an approved forward fix or frontend rollback. A current full backup is not verified. No destructive down migration is provided. Full staging checklist: docs/STAGING_VALIDATION_013_016.md.

Focused local fixtures cover unpublished/published/closed media visibility, owner isolation, private saved/enquiry/plan/courier data, spoofing rejection, recipient-only replies, no booked state and existing-policy/bucket preservation. HTTP image signing and real two-account staging sessions remain unverified. These results are not permission to apply the drafts.
