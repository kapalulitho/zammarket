# Food, ticketing and operational Delivery drafts

29 October 2026. **All three remain HOLD, including their default-FALSE operational gates.** They are new-object clean installs, not upgrades or approvals to change production. Existing 013_v2/014_v2/015/016 remain unchanged and HOLD. No frontend calls these new operational RPCs. No payments, live orders, tickets, assignments or tracking were activated.

## 017 — Food ordering foundations

New tables: food_operation_settings (singleton/enabled), food_restaurants (public name/location/cuisine/hours, owner, approval/status/accepting flags), food_menu_items (restaurant, description/allergens/category, ZMW minor-unit price, availability and optional units), food_orders (customer/merchant, idempotency key/request, authoritative subtotal, state/revision/time), food_order_lines (menu item, name/price snapshots, quantity). Full exact columns are in the SQL.

RLS is enabled on all five tables. Four SELECT policies: approved published restaurant or owner; menu through visible restaurant; orders only customer/merchant; lines through participant orders. Settings are not client-readable/writable. Clients have SELECT only, never direct operational INSERT/UPDATE/DELETE. Catalogue writes are restricted to a trusted service-role workflow; owner catalogue-management RPCs still need design. Supabase default service-role grants are explicitly revoked before the narrow grants are applied.

food_create_order(uuid,jsonb,uuid) is SECURITY DEFINER with empty search_path and authenticated-only execution. It derives the customer from Auth, requires verified profile completion and the disabled-by-default gate, rejects self-ordering and malformed/duplicate items, limits lines/quantities and open orders, serialises per-user idempotency, locks restaurant/menu rows, checks authoritative availability/stock, snapshots names/prices and decrements limited units atomically. No client total/owner/fee fields are accepted. Retry with identical payload returns the original order; key reuse with another payload fails. Failed validation rolls back all writes.

Public restaurant/menu fields include publisher identity, public menu prices and allergen text; no private customer fields are exposed publicly. Order payload contains menu IDs/quantities only. No address/payment credentials are collected here.

**Production blockers:** authoritative opening-hours logic and fulfilment rules, merchant acknowledgement/cancellation/refund transitions, audit trail for fulfilment, tax/delivery fee quotes, moderation/approved provider workflow and concurrent multi-session load validation. Current subtotal is items only, not a full checkout quote. No cancellation/stock-restoration RPC is supplied yet; no activation should occur until that lifecycle is complete.

## 018 — Event reservations

Depends on corrected 013_v2 community_entries and membership helper; 014_v2 is not a technical dependency. New ticket_operation_settings, event_ticket_categories and event_reservations. Categories have event, label, authoritative price/currency, capacity/allocated and active flag. Reservations have buyer/organiser/event/category, quantity/price snapshot, held/cancelled state, idempotency key, creation and cancellation actor/time.

RLS on all three tables. Active categories of published events are public; owners may inspect inactive categories. Reservations are buyer/organiser-only. No attendee directory, private contact fields or raw reservation data is public. Client tables are read-only. Trusted category management grants exclude allocated-counter updates; ordinary clients cannot edit prices/capacity/counters.

reserve_event_tickets(uuid,integer,uuid) requires verified membership and default-FALSE gate, serialises idempotency and per-buyer activity, locks the category and event, checks active future event, prevents organiser self-reservation, caps quantities and active holds per buyer/event and allocates capacity atomically. Price is read from the category. cancel_event_reservation(uuid) is participant-only, uses the same category-first lock order, releases capacity once and records cancellation metadata. Cancellation remains possible when new reservations are disabled. Duplicate cancellation does not release extra units. Functions have empty search_path, authenticated-only execution and no anonymous access.

**Production blockers:** real ticket issuance/check-in, paid/free confirmation rules, organiser approval, reviewed fees/refunds, hold duration/expiry and concurrent-session stress tests. Current reservations have no automatic expiry; no jobs/cleanup are scheduled. Any expiry mechanism needs separate approval. No payment receipt, QR code or confirmed ticket is created by this draft.

## 019 — Delivery operational foundations

Independent of 016's planning tables and does not alter them. New delivery_operation_settings, delivery_courier_approvals, delivery_jobs, delivery_job_events and delivery_job_contacts. Jobs keep areas/parcel, customer/courier, idempotency, state/revision/time; exact addresses/phone are in a separate restricted table. No GPS, payment, fare or provider integration exists.

RLS on all five tables. Four SELECT policies: courier sees their own non-sensitive approval columns; jobs/events are participant-only; contacts are customer-readable or accessible to the assigned approved courier only while accepted/picked_up/in_transit. A courier loses new contact access on completion/cancellation/revocation. The approval operator ID is not granted to ordinary clients. No client can self-approve, assign, direct-write status, create contacts through the frontend or edit/delete audit entries.

submit_delivery_job(text,text,text,uuid) requires verified membership, gate, bounded area/parcel fields, per-customer idempotency and ten-open-request limit. It derives customer identity and inserts an initial audit event. assign_delivery_job(uuid,uuid,bigint) is executable ONLY by service_role, checks approved distinct courier and current submitted revision, then records assignment. advance_delivery_job(uuid,bigint,text) checks verified actor, locked expected revision, assigned approved courier and allowed state/action. Customer cancellation is limited to pre-collection states; new progression requires the gate. Each transition increments revision and inserts a unique revision event. No arbitrary role/status/assignment parameters are accepted from clients.

**Production blockers:** secure operational provider approval/admin audit, exact-contact submission/retention/consent workflow, late cancellation/disputes, reassignment and revoked-courier recovery, proof of delivery and notification reliability. Service assignments may have a NULL actor_id (system actor); an accountable operator audit context is required before real dispatch. RPC revision checking prevents stale retries but a full transition command-idempotency protocol is still required. No real dispatch or public driver directory is connected.

## Shared assessment, tests and rollback

All operational gates initialise FALSE and fail closed if the setting row is missing. Users cannot read/change settings. New functions use fully qualified objects and empty search_path; EXECUTE is explicitly revoked from public/anon and granted to intended roles only. Existing schema/policies, users, listings, likes, messages and photos are not modified. New FKs can block future hard deletion of referenced users; no cascade, deletion worker or cleanup job is enabled. Applying these sources cannot itself invoke the operational functions or enable gates.

Local PGlite fixtures exercised gate denial, server pricing, duplicate-key handling, stock exhaustion, ticket capacity/cancellation, participant isolation, service-only assignment, stale/unauthorised transitions, audit revisions and terminal contact revocation. These are sequential disposable tests, not live Supabase/concurrency/Storage tests. Existing policy definitions remained intact. A verified third test account was created only inside the local fixture to distinguish membership rejection from outsider-role rejection.

Recommendation: **HOLD all three for staged validation and the blockers above.** No production-ready claim. Read ISOLATED_STAGING_SETUP.md and STAGING_VALIDATION_013_016.md. The staging baseline is also HOLD and must never run on production. Each file is transactional with 5s lock/60s statement timeouts; failures before commit can be rolled back. After commit/new data, preserve evidence and use an approved forward correction/frontend rollback. Do not blindly drop tables/buckets or overwrite a populated database. A current production backup has not been verified.
